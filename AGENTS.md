# AGENTS.md

Context for whoever maintains welcome-home next, person or agent. The [README](README.md) describes each feature in detail and [docs/runbook.md](docs/runbook.md) covers production operations; this file is the map: what the app is for, how it is built and why, how it is tested, and where it could go next.

## What it is

A private web app where a few owners connect their Nuki account and create date-bound links that open their door, and their building's entrance if a Nuki Opener opens it: a guest opens the link on their phone and slides to open, with no app, account or code.

**Roles**

- **Owner**: connects Nuki by authorizing welcome-home in Nuki (OAuth2) or with an API token, imports locks, creates, edits, regenerates and revokes links, reads each lock's history.
- **Admin**: an owner who can also invite owners, list them, create passkey recovery links and delete owners. Admins never see other owners' locks, links or history.
- **Guest**: no account; has only a link.

**In production**: a Dockge stack on `docker.fritz.box` (an LXC), reached only through its own Cloudflare Tunnel. Its public URL is not in this repository: `https://welcome-home.example.com` stands for it. Image `ghcr.io/jfisbein/welcome-home`, at the major version's tag (`:v2`). From the development machine the LXC is reached through Proxmox, whose host key is known: `ssh root@proxmox`, then `pct exec 101 -- <command>` (container 101, `dockge`); the stack is `/opt/stacks/welcome-home`, its secrets in `secrets/` there. `docker.fritz.box` itself is not in the development machine's `known_hosts`: do not accept its key blindly.

## Requirements

Functional:

- Registration only by single-use invitation (72 h); sign-in only with passkeys, no passwords. The first admin comes from a command line invitation (`--bootstrap-admin`).
- An owner connects Nuki by authorizing welcome-home in Nuki (OAuth2), or by pasting a Nuki Web API token. Either is checked against Nuki before it is stored, encrypted; an OAuth2 access token is refreshed before it expires. A 401 from Nuki, or a refresh it refuses, marks the connection `DISCONNECTED`, and a daily job checks every connection.
- Locks are imported from Nuki, smart locks and Nuki Openers alike; each has a name, a time zone (from Nuki where possible) and can be deactivated when it leaves the Nuki account. A smart lock may have one of the owner's Openers as its building entrance: its links then open both, the entrance first.
- A link has a label and a validity window entered in the lock's time zone and stored in UTC. Its state (pending, active, expired, revoked) is computed, never stored.
- A guest's GET never acts on the lock: only a POST after sliding to open unlatches (link previews in WhatsApp, Telegram or Slack make GETs). The guest learns whether the door opened, failed, or was refused in night mode.
- Every attempt with a valid link is recorded with IP address and browser; attempts are purged after a retention (365 days).
- Owners who lose their passkey get a recovery link (admin panel or `--recover-owner`); they keep their other passkeys.
- Owners get emails about their locks (opened, failed, denied, Nuki disconnected) and choose which ones, once they have verified their address with the link sent when they register.
- Spanish, English, French, German and Italian: a guest's pages in their browser's language, an owner's pages and emails in the language they chose.

Non-functional:

- Owners are isolated from each other in the database itself (Row-Level Security), not only in code.
- Secrets at rest: Nuki tokens are encrypted (AEAD, bound to their owner and kind); links store no token at all (HMAC).
- Never two unlatches for one press: one action per lock at a time, and the unlatch is never retried once Nuki may have run it.
- Single instance: rate limits, the per-lock mutex and scheduled jobs live in memory in one process.
- GDPR: guests' IP addresses expire; a deleted owner's data is gone from backups after their 30-day retention.
- Upgrades within a major version are pulling the new image: no backup, no change on the server, and rolling back is pinning the previous release.

Out of scope so far: geofencing, push notifications, use limits, recurring schedules, Ring to Open, native apps.

## Architecture

A modular monolith: one Spring Boot app is the only component that talks to Nuki, Postgres and the secrets. Modules are the packages under `welcomehome`, checked by `ModularityTests` (Spring Modulith): a module uses another only through its public types.

| Module   | Responsibility                                                                                              |
|----------|-------------------------------------------------------------------------------------------------------------|
| `auth`   | Security configuration, passkey sign-in, registration from an invitation or recovery link (`OwnerRegistration`), the owner's passkeys page (`PasskeysController`), preferences (`PreferencesController`: language in `owner`, color theme in the `theme` cookie, `Theme`), what every page's menu and `<html>` need (`NavigationModel`), `CurrentOwner` |
| `admin`  | Invitations and recovery links (`InvitationService`), the admin panel, the `--bootstrap-admin` and `--recover-owner` commands |
| `config` | `WelcomeHomeProperties`: the public URL (`BASE_URL`), checked once at startup, from which every module builds its links; `Languages`: the languages with a bundle; depends on no other module |
| `crypto` | Keysets (`Keysets`, `KeysetGenerator`, `KeysetRotator`), `CryptoService` (AEAD), `LinkTokenSigner` (MAC)  |
| `db`     | `OwnerTransactions`: runs work in a transaction with `app.owner_id` set for Row-Level Security             |
| `nuki`   | The only module that talks to Nuki: `LockProvider` (interface), `NukiWebLockProvider`, `NukiWebClient`, connections (`NukiConnections`: an API token or OAuth2 tokens, refreshed before they expire) and their daily check, connecting with OAuth2 (`NukiAuthorizationController`), Nuki's webhooks reporting the outcome of an action (`NukiWebhookController`, `ActionReports`) |
| `locks`  | Import (`LockSync`), settings and state of each owner's locks, smart locks and Openers, and a lock's entrance |
| `links`  | Access links: create, list, edit, regenerate, revoke (`AccessLinks`, `LinkStatus`, `LinkUrls`)            |
| `access` | The guest flow: guest page, `POST /api/open` (`OpenDoor`), rate limits, client IP, per-lock mutex (`LockActions`), unlatch confirmation |
| `audit`  | Access events, history pages, the home page's latest attempts (`RecentAttempts`), both drawn from `AttemptRow`s (`AttemptRows`: time in the lock's zone, outcome and country in the reader's language), purge job; publishes `AccessAttempted` |
| `welcomehome` (root package, not a module) | What spans modules: the home page (`HomeController`), `/settings` and the former addresses of its sections (`SettingsController`), the error pages (`ErrorPages`) |
| `notifications` | Emails to owners (opened, failed, denied, Nuki disconnected) by their preferences, and always about their account (recovery link created, passkey added), sent after commit (`OwnerNotifier`) |

**Guest flow** (`access.OpenDoor`): rate limit per IP → the link exists, its MAC is valid and it is not revoked (`resolve_link`, a `SECURITY DEFINER` function, is the only way to read a link without an owner context) → rate limit per link → within its dates → lock active → owner's Nuki connection OK → in the owner's context, unlatch under the lock's mutex (a second guest waits and gets the same result) → wait for whichever tells first, within 15 s: Nuki's webhook reporting the outcome, for an owner connected with OAuth2, who unlatches through Nuki's Advanced API; or the lock's log showing an unlatch with trigger 0 or 4 (not by hand, button or accessory) → record the event. A slide at the building entrance (`"door": "entrance"`) goes the same way with the lock's Opener in place of the lock: Opener active, Nuki's action 3 (the electric strike), under the Opener's mutex, recorded with the link's lock and the Opener.

**`LockProvider`** (`listLocks`, `getState`, `unlatch`, `getRecentLog`, all by owner id) isolates Nuki: tokens are decrypted inside `nuki` and never leave it. Another way to reach a lock (Nuki Bridge, MQTT) is another implementation or a change inside `nuki`, without touching the rest.

**Data model** (`src/main/resources/db/changelog/changes/`): `owner` (`language`, and the email's verification: `email_verified_at`, the link's hash and expiry; the only columns `app_user` may update), `invitation` (also recovery links: `recovers_owner_id`), `nuki_connection` (`credential`: `API_TOKEN` or `OAUTH2`; `access_token_encrypted`, and for OAuth2 `refresh_token_encrypted` and `access_token_expires_at`), `lock` (`device_type`: `SMART_LOCK` or `OPENER`; `entrance_lock_id`, the Opener at a smart lock's building entrance), `access_link` (`token_version`), `access_event` (`ip`, `country`, and `entrance_lock_id` for an attempt at the entrance; `lock_id` is always the link's lock), `notification_preference`, and Spring Security's `user_entities` and `user_credentials`. Every table with `owner_id` has Row-Level Security with a policy that fails closed (`owner_id = nullif(current_setting('app.owner_id', true), '')::uuid`). `owner` and `invitation` have no `owner_id` and no RLS: only `auth` and `admin` use them. Neither do the passkey tables, keyed by the owner's email: `auth` joins `user_entities` by email in every query.

**Tables by module.** Spring Modulith checks only Java dependencies; SQL crosses modules in the places below, all reads for display or a daily job, except `admin` deleting an owner. Anything else goes through the owning module's public types.

| Table | Owner | Also used in SQL by |
|-------|-------|---------------------|
| `owner` | `auth` (registration inserts it) | `admin`: lists owners and deletes one; `audit`, `nuki`: owner ids for their daily jobs; `notifications`: the owner's email |
| `user_entities`, `user_credentials` | `auth` (Spring Security's passkey store) | `admin`: deletes an owner's passkeys |
| `invitation` | `admin` | none (`auth` goes through `InvitationService`) |
| `nuki_connection` | `nuki` | none |
| `lock` | `locks` | `links`: lock names in link lists; `audit`: names and time zones in the history and the home page's attempts; `notifications`: name and time zone; `resolve_link` |
| `access_link` | `links` | `audit`: labels in the history; `notifications`: labels; `access`: only through `resolve_link` |
| `access_event` | `audit` | none |
| `notification_preference` | `notifications` | none |

**Roles in Postgres**: `migrator` owns the schema and runs Liquibase; the app connects as `app_user`, with no ownership and no `BYPASSRLS`. No `FORCE ROW LEVEL SECURITY`, so that `resolve_link` (owned by `migrator`) sees the link. Roles come from `deploy/db-init/01-create-roles.sh`, used by development, tests and production alike.

**Jobs** (`@Scheduled`, server time zone): Nuki connection check (08:00), access event purge (03:30), purge of invitations expired more than 30 days ago (03:35); in production a separate `backup` container dumps the database at 04:00.

**Commands**: `--bootstrap-admin` and `--recover-owner=<email>` start the app without the web server (`WelcomeHomeApplication.runsACommand`), print a link and exit. Anything web-only must stay optional without a web server (see `CommandLineTests`).

## Decisions and why

| Decision | Why |
|----------|-----|
| OAuth2 with Nuki offered first, a pasted API token folded away as the alternative; OAuth2 off without a client id and secret | Nothing to generate or paste, and access renews itself. Nuki grants the client only with its Advanced API (granted to welcome-home on 2026-10-25), so an install without one still works with tokens. |
| The OAuth2 client written in `nuki` (`NukiAuthorizationController`, `NukiWebClient`), not Spring Security's | Spring's stores tokens in clear, and its token client would need customizing for Nuki anyway; what it would save, the `state`, the PKCE verifier and the redirect, is a few lines, covered by `NukiAuthorizationTests`. |
| OAuth2 tokens in `nuki_connection`, encrypted like an API token; one refresh at a time per owner, 5 minutes before expiry; a token request never repeated once Nuki may have answered | Nuki rotates the refresh token: two refreshes with one, or a repeated one, would leave a dead token. A refresh failure is never `NO_ANSWER`, which would tell a guest that the door may have opened. |
| 2.0.0 renamed `api_token_encrypted` to `access_token_encrypted` | Nobody but the owner used the app yet; the changeset has a `<rollback>`, checked once both ways, and the dump taken before upgrading restores 1.x. |
| Unlatch (action 3), confirmed from the lock's log | Nuki runs actions asynchronously: a 204 only means accepted. |
| Owners connected with OAuth2 unlatch through Nuki's Advanced API, whose webhook reports the outcome; the log is read meanwhile, and whichever tells first counts | A guest learns at once whether the door opened, rather than when the log shows it. The log stays because the webhook is not sure to come: Nuki documents no retries, turns a client's webhooks off after too many failures, and sends none for an API token, which is the owner's own. Only reports of actions are used, matched in memory by their request id (single instance), so no owner is looked up without an owner context. The `webhook.central` scope is asked for but not required: Nuki's central webhooks, the only ones that report the Advanced API's actions, need it, and without it Nuki refused an advanced unlatch with a 401 (2026-10-28); a client whose Advanced API has no webhooks may not ask for it, so on `invalid_scope` the owner is sent to Nuki once more without it. A refused advanced request (4xx other than 429) ran nothing, so the plain action follows; one Nuki may have run is never repeated. The webhook's credential is Nuki's signature with the client secret, so it has no CSRF token or session. |
| A Nuki Opener is a lock of another type in the same `LockProvider`, and a smart lock may name one as its building entrance, whose slide its links' guest page shows first | Nuki's Web API lists Openers among its smartlocks and opens them with the same action, so no adapter of its own; and a guest who must pass a building's entrance and then a door needs both from one link (the user's choice, 2026-10-27, over separate links per device). `access_event.lock_id` stays the link's lock, the Opener going in `entrance_lock_id`, so link histories, emails' history links and the previous release keep reading events as before. Nuki does not document how an Opener logs an opening: it is taken to be a lock's unlatch, and an unconfirmed opening logs what the log showed. |
| The unlatch is retried only on 429 or when no connection was made | Retrying after Nuki may have run it could open the door twice. |
| Passkeys only, invitations only | No passwords to leak; a private app with few, known users. |
| Links are `{link_id}.{HMAC(link_id, token_version)}` | Nothing to steal from the database; a URL can be shown again; incrementing `token_version` invalidates every earlier URL. |
| Row-Level Security plus `owner_id` in every query | Isolation does not depend on every query being right. `OwnerIsolationTests` checks every route with an id. |
| AEAD with the owner id as associated data | A ciphertext copied to another owner's row does not decrypt. |
| Admins see only emails and dates | An admin is still just an owner to RLS. Recovery links are the exception the user chose: whoever holds one signs in as that owner, so the admin who creates one could. The owner is emailed when one is created and when a passkey is added, so its use is not hidden from them. |
| Recovery adds a passkey and keeps the old ones | The user's choice; the owner then deletes the lost device's passkey at `/settings/passkeys`, which never deletes the last one. |
| `CF-Connecting-IP` for the guest's IP, `forward-headers-strategy=framework` | The tunnel is the only way in, so Cloudflare's headers are trustworthy; `X-Forwarded-For` starts with whatever the client sent. |
| `/o/{token}` masked in logs, `Referrer-Policy: no-referrer`, `noindex` | Guest URLs are bearer credentials. |
| No CSRF token on `POST /api/open`, and no session for guests | The link's token in the body is the credential, which a forged request would need anyway; a CSRF token kept in the session went stale when a guest opened more than 30 minutes after loading the page. |
| No ports published; own cloudflared in the stack | With a published port the app was reachable from the LAN and the forwarded headers could be spoofed. |
| Database passwords as files (`configtree:`), keysets as Docker secrets | No secrets in environment variables or in the image. |
| Keysets backed up apart from the dumps (Vaultwarden) | A stolen dump alone does not expose the Nuki tokens. |
| Releases are `vX.Y.Z` tags; production follows the major version's tag (`:v2`) | Upgrading is Dockge's Update, with no backup and no change on the server. The running release is the image's `org.opencontainers.image.version` label; rolling back is pinning the previous one. It holds because releases within a major are backward compatible (Conventions). |
| Emails are sent after commit, on another thread, and dropped if they fail | A guest never waits for SMTP, and a mail problem never fails an opening. At most one email about refused attempts per link per hour. |
| Guests slide to open (a native `input type="range"`), not press a button | A touch by mistake, in a pocket or while scrolling, must not open the door. A native range, so keyboards and screen readers work it; `open.js` undoes a jump to where the track was touched and moves a quarter per key. After an opening it works again a minute later, after a failure at once, after expired, revoked or invalid never. |
| Configuration's pages under `/settings/...`, their former addresses redirecting (301) | Emails already sent link to `/nuki/connection`, `/notifications` and `/passkeys`: within a major version, every URL already sent keeps working. |
| The app's own error page; `/error` public; the session only in its cookie | Spring Boot's page broke the app's look, and a guest's error on a public route was redirected to /login, starting a session whose id Tomcat put in the URL (`;jsessionid=`). An unknown address still sends a visitor who is not signed in to /login, so no route shows it exists. |
| The color theme in a cookie, not in the owner's row | The user's choice: it belongs to the browser, so a phone and a laptop may differ, and it also applies to the pages before signing in. The server writes `<html data-theme>`, so no script and no flash of the other theme; no cookie means the system's. |
| Pico CSS 2.1.1 kept, though Pico is unmaintained since 2.1.1 (repositories archived) | It is a static CSS file served from `static/css/` with no JavaScript, so there are no fixes to miss, and what it lacks goes in `app.css`. The templates lean on its classless styling of semantic HTML (`article`, `nav`, `fieldset role="group"`, `aria-busy`, `aria-current`, automatic dark mode): Bootstrap, Bulma or Pure would mean adding classes to every template for no visible gain, and Pure is barely maintained either. Revisit if a browser starts drawing something wrong that `app.css` cannot fix cheaply, or for a redesign; then prefer a fork of Pico, or own CSS keeping its variables. |

## Conventions

- **Language**: code, comments, javadoc, docs and commit messages in English. Table, column and enum names in English. UI texts only in `i18n/messages*.properties` (Spanish the default bundle; English, French, German and Italian the others): never in Java, templates or JavaScript, which `TemplateTextTests` checks. A message with markup goes through `th:utext`, with every value escaped by `#strings.escapeXml`; an apostrophe in a message is written `''`. A new language: the README's "Adding a language".
- **Javadoc** on every public class and method (`-Xdoclint:all -Werror` fails `check`). Comment the why, sparingly.
- **Nullness**: everything is non-null unless `@Nullable` (JSpecify); every package has `@NullMarked`; NullAway fails the build. Spring 7's `JdbcClient.query(X.class).list()` returns `List<@Nullable X>`: use `new SimplePropertyRowMapper<>(X.class)` or a lambda for lists.
- **Compatibility**: within a major version every release is backward compatible, as production pulls `:vN` without reading release notes and rolls back by pinning the previous release. So: the previous release runs against the new schema; no new required property, secret or environment variable (a new one has a default); nothing to change in `deploy/`; every URL already sent keeps working (guest links, invitations, recovery and verification links, history URLs). Migrations only expand the schema: new tables, nullable columns or columns with a default, indexes, grants; never drop, rename or retype, never add NOT NULL or UNIQUE to what exists, never revoke, every changeset in a transaction. `MigrationCompatibilityTests` checks the changesets from `COMPATIBLE_FROM` on. Anything else waits for the next major, which moves `COMPATIBLE_FROM` past its breaking changesets and production to `:vN+1`.
- **Liquibase**: XML with native tags; `<sql>` only for CHECK constraints, RLS, GRANTs and functions. A new table with `owner_id` gets `ENABLE ROW LEVEL SECURITY`, its policy and its grants to `app_user` in the same changeset (`MigrationTests` fails otherwise).
- **Data access**: `JdbcClient` with records; owner data only inside `OwnerTransactions.execute/run`, with `owner_id` in the query as well. No `findById(id)` without an owner.
- **Configuration**: `application.yaml` (and `application-dev.yaml`); `@ConfigurationProperties` records; durations in ISO-8601 (`PT1M`).
- **Web**: Thymeleaf templates, Pico CSS classes; every page's `<html>` carries `th:lang="${#locale.language}"` and `th:attr="data-theme=${theme}"`; every signed-in page starts with `fragments/layout :: menu('<section>')` (home, locks, settings or admin), and configuration's pages add `settings('<section>')` (nuki, preferences, notifications or passkeys); guests' attempts are drawn by `fragments/attempts :: table(attempts, withLock)`, on the home page and in the history alike; a page that must start no session sets `sessionless`, so the layout leaves out the CSRF meta tags. Two Thymeleaf traps: a fragment selector also matches elements by name, so no fragment is named like an element (hence `menu`, not `nav`); and `th:replace` runs before `th:if` on the same element, so a conditional fragment goes inside `<th:block th:if>`. The CSP also forbids inline styles: scripts change styles only through the DOM (`element.style`), never `<style>` or `style=` in markup; CSRF on every form, HTML forms send PUT/PATCH/DELETE through `_method`. JS in `static/js/`, one small file per behavior, no inline scripts (CSP `script-src 'self'`); a script's texts come from its page, as hidden lists or `data-*` attributes. Routes taking an id must be covered by `OwnerIsolationTests` (a guard test lists them).
- **Commits**: one per task, pushed to `main` once `./gradlew build` is green.

## Testing strategy

`./gradlew build` compiles (Error Prone, NullAway), runs every test and checks javadoc. Most tests are integration tests (`@IntegrationTest`): a real Postgres in Testcontainers, initialised with the production role script, migrated by Liquibase as `migrator`, used by the app as `app_user`, with freshly generated keysets.

- **Nuki**: never the real API in tests. `NukiStandInConfiguration` starts WireMock in place of `api.nuki.io`; `NukiWebClientTests` covers status codes, timeouts, retries and backoff, and the token endpoint; `NukiAuthorizationTests` the way to Nuki and every way back; `NukiTokenRefreshTests` refreshing (once for simultaneous calls, disconnecting when refused, never `NO_ANSWER`); `NukiConnectionWithoutAuthorizationTests` the app without an OAuth2 client; `NukiWebhookTests` Nuki's webhooks: the signature (checked against Nuki's own example), reports matched by request id whichever arrives first, error codes, and what is refused or ignored.
- **Passkeys**: `PasskeyEmulator` (webauthn4j-test) answers registration and sign-in like a browser with an authenticator, so the real WebAuthn endpoints are exercised end to end.
- **Isolation**: `OwnerIsolationTests` (every id route answers 404 for another owner and changes nothing), `MigrationTests` (every `owner_id` table has RLS and its policy), `RowLevelSecurityTests` (what `app_user` sees with and without an owner context), `ModularityTests` (module boundaries), `AdminPanelTests` (admins see no locks or links).
- **Guest flow**: `OpenDoorTests` (order of checks, results, confirmation from the log or Nuki's webhook, the Advanced API's fallback to the plain action, concurrency, client IP, the building entrance), `LockActionsTests` (one action per lock), `TokenLoggingTests` (tokens never logged), `GuestPageTests` (a GET never calls the lock provider; one slider per door).
- **Pages**: `HomePageTests` (locks, latest attempts, the same rows as the history, the menu and `/settings`), `ThemeTests` (the theme cookie and `data-theme` on every page), `SignedInErrorPageTests` (the error page with the menu, through MockMvc and `/error`). What MockMvc does not show runs against a real server (`@IntegrationTest(webEnvironment = RANDOM_PORT)`): `ErrorPagesTests` (errors forwarded to `/error`, no session for guests, JSON for scripts) and `SessionCookieTests` (cookie flags, the session never in a URL).
- **Commands**: `CommandLineTests` starts the app without the web server.
- **Emails**: `MailStandInConfiguration` starts GreenMail as the SMTP server; `NotificationTests` checks each kind of email, preferences, the per-link quiet period, the owner's language and that two simultaneous rejections send one email; `AccountSecurityEmailTests` the recovery and passkey emails; `EmailVerificationTests` the link that verifies an owner's address, and that nothing else goes to it before.
- **Languages**: `MessageBundlesTests` (bundles have the same keys and each message the same arguments, apostrophes are doubled, templates name only existing ones), `PagesInEveryLanguageTests` (every page in every language, no missing text), `TemplateTextTests` (no text in templates, escaped `th:utext`), `OwnerLanguageTests` (an owner's language, and that `app_user` may update no other column of `owner`).
- **Practice**: start with `git fetch`: the development clone has been dozens of commits behind `origin/main`, which is where work from other machines and release merges land. Each change is checked with a mutation test by hand (break the code, see a test fail, restore it), and deployment changes are tried on a local copy of the production stack (`COMPOSE_PROJECT_NAME=...` to stay apart from the development database).
- **By hand in a browser**, for what no test runs: the JavaScript (`open.js` above all) and how pages look, in light and dark and at phone width. Run the dev app (`docker compose up -d`, `./gradlew bootRun`) and use Chrome; owner pages need the owner's passkey, which only the owner can use (sessions live in memory, so a restart signs them out). Sample rows go into the development database as its superuser (`docker compose exec -T db psql -U postgres -d welcome_home`) and are deleted afterwards. For the guest page to offer opening without any risk, add a `nuki_connection` with status `OK` and `api_token_encrypted` set to `'\x00'`: the token does not decrypt, so an opening fails as unavailable before anything reaches Nuki. Never with a real token. Chrome's window does not shrink below about 616 px: for phone widths the owner switches on DevTools' device mode, and sizes are read with JavaScript (`innerWidth`, `scrollWidth`).

Never call Nuki's unlatch for real outside a guest sliding to open: it opens a real door. Development uses a real Nuki token only for read-only calls.

## Build, run, release

```sh
./gradlew build                   # everything CI runs
./gradlew generateKeysets         # development keysets in secrets/ (git-ignored)
docker compose up -d              # development Postgres on localhost:5432
./gradlew bootRun                 # the app on http://localhost:8080 with the dev profile
./gradlew rotateAeadKeyset --args=<file>
```

`.github/workflows/image.yml`: pull requests build, test and build the image without pushing; pushes to `main` publish `edge`; tags `vX.Y.Z` publish `vX.Y.Z`, `vX` and `latest` (prereleases only their own tag), and then create the GitHub release.

Release: a pull request named `Version X.Y.Z` from branch `release-X.Y.Z` that bumps `version` in `build.gradle.kts`; once merged, tag the merge commit `vX.Y.Z` and push the tag. Its description becomes the GitHub release's notes, so it is written for whoever deploys: what changed since the last release, and anything to do before deploying. The workflow drops its first paragraph when it starts with "Sets the project's version", and Claude Code's attribution (`.github/scripts/release_notes.py`). Production follows `:v2`, so `deploy/compose.yaml` changes only for a new major version. Upgrading production and everything else on the server is in the runbook.

**Nuki's OAuth2, as checked by hand on 2026-10-25** with read-only scopes (Nuki's current guide is docs.nuki.io/guide/authorization/oauth2; older guides and forum posts describe outdated endpoints):

- Nuki granted welcome-home's Advanced API on 2026-10-25, of a type without webhooks or advanced actions (see Where things stand); the owner deleted it and applied again on 2026-10-28, as "Smart Home", which Nuki's guide (docs.nuki.io/guide/overview) lists with OAuth2 and webhooks ("Short Rental" needs a Smart Hosting subscription per lock), with a 500-character description, and Nuki granted it that day with the same client id and secret. Its tab in Nuki Web shows the client id and secret and lists the callback URLs, `https://welcome-home.example.com/nuki/callback,http://localhost:8080/nuki/callback`. Production keeps them in the stack's `secrets/nuki-oauth-client-id` and `secrets/nuki-oauth-client-secret`; development reads them from `secrets/config/welcomehome.nuki.oauth.client-id` and `secrets/config/welcomehome.nuki.oauth.client-secret`.
- Nuki's authorization server is ORY Hydra at `oauth.nuki.io` (seen 2026-10-26): `GET https://api.nuki.io/oauth/authorize` answers 303 to `https://oauth.nuki.io/oauth2/auth` with the query unchanged, and Hydra's discovery document, `https://oauth.nuki.io/.well-known/openid-configuration`, lists `code_challenge_methods_supported` `plain` and `S256`, and a `revocation_endpoint` (`https://oauth.nuki.io/oauth2/revoke`). A malformed `code_challenge` or an unknown method still reaches Nuki's sign-in page: Hydra checks them only after the owner consents, and the verifier at `POST /oauth/token`. The app sends PKCE (`code_challenge` S256 to `/oauth/authorize`, `code_verifier` to `/oauth/token`) since 2026-10-26; that day the owner connected with it in development (`OAUTH2`, `OK`, with a refresh token). Whether Nuki refuses a wrong verifier was not tried.
- `GET /oauth/authorize` sends the owner back with `code`, `scope` and the `state` whole; `POST /oauth/token` with the client's id and secret both as HTTP Basic and in the form answers `token_type` `bearer`, `expires_in` 3599, `scope`, `access_token` and, with `offline_access`, `refresh_token`; `grant_type=refresh_token` answers new access and refresh tokens. The refresh token rotates on every refresh; whether the previous one still works was not checked, so the app assumes it does not. Nuki's guide says refresh tokens last 90 days and that, if the access token is not refreshed within them, the owner must authorize again; whether each refresh starts a new 90 days or they count from the authorization, it does not say. The daily check refreshes every owner, so with the first reading no owner ever has to connect again; with the second, every owner would every 90 days (and get the disconnection email). The owner's production connection, made on 2026-10-26, tells on 2027-01-24. The tokens are opaque, not JWTs, so they do not tell either.
- Nuki's rate limits (docs.nuki.io/guide/endpoints/rate-limits): 4 requests per second, 100 per minute, 1000 per hour, then 429 until the window passes; the page does not say whether per token, account or client. One guest's opening (an unlatch and up to about 8 reads of the log) takes more than a day's refreshes; the daily check, 2 requests per owner in a row, would only near 100 per minute at about 50 owners, if the limit is per client.
- Nuki's consent page ("A welcome-home le gustaría:") lists each scope with Nuki Web's labels for API tokens, seen with all four on 2026-10-26: in Spanish, `smartlock.log` "Ver el protocolo de cierre y recibir notificaciones de registro", `smartlock.readOnly` "Ver dispositivos", `offline_access` "Mantener el acceso a los datos hasta su revocación" (its description says the owner can revoke it at any time), and `smartlock.action` "Gestionar dispositivos" ("Se permite operar dispositivos Nuki"). **Other ideas**, roughly by value:

- Owners who cannot use a passkey. First learn why: today almost every device can hold one (iCloud Keychain, Google Password Manager, Bitwarden or 1Password), a computer without one can use the phone's by scanning a QR code, and a security key costs little; help on the invitation page, by platform, may be all it takes. If a real alternative is needed, a one-time code by email: the owner asks for it with their email, gets 6 digits valid for 10 minutes, and types them in the same browser, which a mail scanner opening a link could not use up, and which ties it to the browser that asked. Only to verified addresses, single use, kept as a hash like the verification link, rate limited by email and IP, and an email to the owner on each sign-in this way. Spring Security has one-time token login (`oneTimeTokenLogin()`), but its JDBC store keeps tokens in clear. It makes the email account the owner's credential, weaker than a passkey: so offer it per owner, or only until they add a passkey, and record the trade-off in Decisions. Passwords would add a secret to leak and still need resetting by email, and TOTP alone is a weak factor: neither is worth it here.
- Re-encrypting stored Nuki tokens after an AEAD rotation, so that old keys can be dropped without owners connecting again.
- Links with a maximum number of uses or a recurring schedule (`access_link` columns).
- Geofence as a deterrent (browsers accept fake locations: store only distance and accuracy, and tell the guest first).
- A local Nuki Bridge or MQTT adapter as another `LockProvider`.
- Cloudflare Access in front of the owner pages, excluding `/o/*` and `/api/open`.
