# Nuki

Read when: anything that calls Nuki, connects an owner to it or reads what it reports: connections, tokens, OAuth2, the unlatch, webhooks, Openers.

See also: [guest flow](guest-flow.md) (what asks for the unlatch), [status](status.md) (what only real use will tell).

## LockProvider

**`LockProvider`** (`findConnection`, `listLocks`, `getSnapshot`, `listSnapshots`, `unlatch`, `getRecentLog`, all by owner id) isolates Nuki: tokens are decrypted inside `nuki` and never leave it. Another way to reach a lock (Nuki Bridge, MQTT) is another implementation or a change inside `nuki`, without touching the rest.

## Decisions

| Decision | Why |
|----------|-----|
| OAuth2 with Nuki offered first, a pasted API token folded away as the alternative; OAuth2 off without a client id and secret | Nothing to generate or paste, and access renews itself. Nuki grants the client only with its Advanced API (granted to welcome-home on 2026-10-25), so an install without one still works with tokens. |
| The OAuth2 client written in `nuki` (`NukiAuthorizationController`, `NukiOAuthClient`), not Spring Security's | Spring's stores tokens in clear, and its token client would need customizing for Nuki anyway; what it would save, the `state`, the PKCE verifier and the redirect, is a few lines, covered by `NukiAuthorizationTests`. |
| OAuth2 tokens in `nuki_connection`, encrypted like an API token; one refresh at a time per owner, 5 minutes before expiry; a token request never repeated once Nuki may have answered | Nuki rotates the refresh token: two refreshes with one, or a repeated one, would leave a dead token. A refresh failure is never `NO_ANSWER`, which would tell a guest that the door may have opened. |
| 2.0.0 renamed `api_token_encrypted` to `access_token_encrypted` | Nobody but the owner used the app yet; the changeset has a `<rollback>`, checked once both ways, and the dump taken before upgrading restores 1.x. |
| A 401 disconnects only if a read repeats it, and a disconnection is tried again hourly for 7 days | Disconnecting stops every link of the owner, so a passing mistake of Nuki's must not do it, nor last until the owner notices. Credentials stay stored while disconnected, which makes trying them cheap; 7 days bounds the requests for an access truly revoked. The owner is emailed both ways, under the same preference. |
| Disconnecting Nuki or deleting an owner revokes an OAuth2 authorization at Nuki, best effort | Deleting the tokens here leaves them valid at Nuki, with encrypted copies in dumps for 30 days. Revoking the refresh token ends its access tokens too (RFC 7009). A failure is logged and changes nothing else, as the owner asked to leave. The endpoint is Nuki's `revocation_endpoint`, at `oauth.nuki.io`; a request there without credentials answers 400, and at `api.nuki.io`, 404. It takes the client's credentials only as HTTP Basic: with them also in the form, as the token endpoint takes them, it answers `invalid_client`, so no revocation worked before 2026-11-04. Connecting again does not revoke the tokens it replaces. |
| Unlatch (action 3), confirmed from the lock's log | Nuki runs actions asynchronously: a 204 only means accepted. |
| Owners connected with OAuth2 unlatch through Nuki's Advanced API, whose webhook reports the outcome; the log is read meanwhile, and whichever tells first counts | A guest learns at once whether the door opened, rather than when the log shows it. The log stays because the webhook is not sure to come: Nuki documents no retries, turns a client's webhooks off after too many failures, and sends none for an API token, which is the owner's own. Only reports of actions are used, matched in memory by their request id (single instance), so no owner is looked up without an owner context. `smartlock.auth` is required, though welcome-home manages no authorizations: Nuki refuses `/action/advanced` without it (seen 2026-11-04), so Nuki's consent page asks owners to let welcome-home manage their devices' authorizations, and the connect page says why (the user's choice, 2026-11-04, over leaving it optional). The `webhook.central` scope is asked for but not required: Nuki's central webhooks, the only ones that report the Advanced API's actions, need it; a client whose Advanced API has no webhooks may not ask for it, so on `invalid_scope` the owner is sent to Nuki once more without it. A refused advanced request (4xx other than 429) ran nothing, so the plain action follows; one Nuki may have run is never repeated. The webhook's credential is Nuki's signature with the client secret, so it has no CSRF token or session. |
| A Nuki Opener is a lock of another type in the same `LockProvider`, and a smart lock may name one as its building entrance, whose slide its links' guest page shows first | Nuki's Web API lists Openers among its smartlocks and opens them with the same action, so no adapter of its own; and a guest who must pass a building's entrance and then a door needs both from one link (the user's choice, 2026-10-27, over separate links per device). `access_event.lock_id` stays the link's lock, the Opener going in `entrance_lock_id`, so link histories, emails' history links and the previous release keep reading events as before. Nuki does not document how an Opener logs an opening: it is taken to be a lock's unlatch, and an unconfirmed opening logs what the log showed. |
| A refusal at Nuki's token endpoint disconnects an owner only if it is about their code or tokens | A 401, `invalid_client` or `unauthorized_client` is about welcome-home's client, such as a wrong or rotated secret: disconnecting would hit every OAuth2 owner at the next daily check, and correcting the secret would not bring them back. It logs an error and counts as Nuki failing. |
| The unlatch is retried only on 429 or when no connection was made | Retrying after Nuki may have run it could open the door twice. |
| Nuki tokens that an earlier AEAD key encrypted are encrypted with the primary one on every start, each owner's in their turn among refreshes | A keyset changes only with a restart, so one pass then leaves every token on the primary key, and the earlier one can leave the keyset without owners connecting again; before, pasted API tokens and disconnected connections kept it for good. In their turn: a refresh that read the tokens before they changed would not store Nuki's new ones, and Nuki rotates the refresh token. The earlier key stays 30 days, as the dumps taken before the rotation need it (runbook). |

## Tests

- **Nuki**: never the real API in tests. `NukiStandInConfiguration` starts WireMock in place of `api.nuki.io`; `NukiWebClientTests` covers status codes, timeouts, retries and backoff; `NukiOAuthClientTests` where an owner authorizes, the token endpoint and revoking; `NukiAuthorizationTests` the way to Nuki and every way back; `NukiTokenRefreshTests` refreshing (once for simultaneous calls, disconnecting when refused, not when Nuki refuses the client, never `NO_ANSWER`); `NukiConnectionWithoutAuthorizationTests` the app without an OAuth2 client; `NukiWebhookTests` Nuki's webhooks: the signature (checked against Nuki's own example), reports matched by request id whichever arrives first, error codes, and what is refused or ignored. `TokenReEncryptionTests`: on start, tokens of the AEAD keyset's earlier key encrypted with the new one, whatever the connection's status; a token whose key is gone left as it is; a refresh under way keeping the tokens Nuki returned. The test contexts' AEAD keysets are rotated once, as production's is after a rotation.

## What was learned about Nuki

**Nuki's Advanced API works since 2026-11-04, with `smartlock.auth`.** Owners connected with OAuth2 unlatch through it so that a guest learns at once whether the door opened (see [Decisions](#decisions)). It was built from Nuki's guide and API definition as read on 2026-10-27 (docs.nuki.io/guide/webhooks and its pages, api.nuki.io/static/swagger/swagger.json, version 4.23.0) and tested against WireMock, as Nuki cannot reach a development machine. Until then every advanced unlatch in production was refused with a 401, `{"detailMessage":"Your access token is not authorized: Token doesn't match required scopes!"}`, and the plain action opened the door instead, confirmed from the log some 5 to 7 seconds later. The central webhook's secret is the client secret, so nothing new is stored; the owner sets the client's webhook URL in Nuki Web (the runbook's "Nuki's webhook URL"). The app logs every report ("Nuki reported request ..."), a refused advanced request ("Nuki refused to unlatch smartlock ... with its Advanced API"), Nuki's reason, and the scopes Nuki grants, on connecting and on every refresh. Found on 2026-11-04 with throwaway tokens of the client, authorized by hand against the development callback with the app stopped (so that the code stayed in the browser's address bar), and only ever locking a locked door:

- `/action/advanced`, the only advanced call that unlatches, needs `smartlock.auth`: the scopes asked for until then plus `smartlock.auth` were accepted, plus `account` were not, though `/action/lock/advanced` was. Nuki's API definition (4.25.0) still asks only `smartlock.action`, and 2.5.4's `smartlock` had not helped. Nuki's "Web API Webhooks" guide 1.1 (a PDF on developer.nuki.io, uploads/short-url/hFo7pRlqmT79AaS8t2Sl6FdoOqw.pdf) asks in its example for `smartlock smartlock.auth account webhook.central`, which is what led there.
- Nuki sends no webhook, not even a test one, before the first advanced action it accepts; `webhookStatus` (below) appeared with that one. It came from `162.19.223.21` (OVH, Germany), with the user agent `Java/21.0.8`, and Cloudflare's Bot Fight Mode challenged it (403, nothing in the app's log) until an IP Access rule allowed that address (runbook). Then the app answered 204 to reports of `type` `SmartlockAction` for `/action/advanced` and `LockAction` for `/action/lock/advanced`, with `requestId`, `smartlockId` and `success: true` at the top, about 1.6 seconds after the request.
- An `account`-scoped token reads Nuki's side, which Nuki Web shows only in part: `GET /account/integration` (each integration's granted scopes; welcome-home's `advancedType` and `advancedState` stay null, which did not matter), `GET /api/key` and `GET /api/key/{apiKeyId}/advanced` (status, type, webhook URL and features, and `webhookStatus`, `ACTIVE` or `DEACTIVATED`, which Nuki Web does not show; a deactivated one is reactivated with `POST /api/key/{apiKeyId}/advanced/reactivate`), and `GET /api/key/{apiKeyId}/webhook/logs` (the tab's last 300 webhooks, each with the request that caused it).
- Before that: the first client's Advanced API, of type "Only OAuth 2 API Secret", answered 403 and offered no webhooks (Nuki's staff, developer.nuki.io/t/40088, 2026-05: the type changes only by deleting the Advanced API and applying again); applying again as "Smart Home" on 2026-10-28 kept the client id and secret, and its status is `ACTIVE`. Nobody answered the owner's question on Nuki's forum (developer.nuki.io/t/41230); Nuki's guide offers developer@nuki.io for help while integrating (docs.nuki.io/guide/overview/integrator).

What only a guest's real opening will tell:

- how error codes come: the same guide gives `errorCode` as hexadecimal text; the app takes `errorCode` at the top or in the first of `detail`, as hexadecimal text or a number.
- whether an advanced unlatch shows in the lock's log with trigger 0 or 4, as the plain one does; if not, only the webhook confirms it.
- whether Nuki takes the Advanced API from accounts other than the client's own; the client being `ACTIVE`, not `TESTING`, it should. If not, their unlatches fall back to the plain action, with the log line above.

**Nuki's OAuth2, as checked by hand on 2026-10-25** with read-only scopes (Nuki's current guide is docs.nuki.io/guide/authorization/oauth2; older guides and forum posts describe outdated endpoints):

- Nuki granted welcome-home's Advanced API on 2026-10-25, of a type without webhooks or advanced actions (see above); the owner deleted it and applied again on 2026-10-28, as "Smart Home", which Nuki's guide (docs.nuki.io/guide/overview) lists with OAuth2 and webhooks ("Short Rental" needs a Smart Hosting subscription per lock), with a 500-character description, and Nuki granted it that day with the same client id and secret. Its tab in Nuki Web shows the client id and secret and lists the callback URLs, `https://welcome-home.example.com/nuki/callback,http://localhost:8080/nuki/callback`. Production keeps them in the stack's `secrets/nuki-oauth-client-id` and `secrets/nuki-oauth-client-secret`; development reads them from `secrets/config/welcomehome.nuki.oauth.client-id` and `secrets/config/welcomehome.nuki.oauth.client-secret`.
- Nuki's authorization server is ORY Hydra at `oauth.nuki.io` (seen 2026-10-26): `GET https://api.nuki.io/oauth/authorize` answers 303 to `https://oauth.nuki.io/oauth2/auth` with the query unchanged, and Hydra's discovery document, `https://oauth.nuki.io/.well-known/openid-configuration`, lists `code_challenge_methods_supported` `plain` and `S256`, and a `revocation_endpoint` (`https://oauth.nuki.io/oauth2/revoke`). A malformed `code_challenge` or an unknown method still reaches Nuki's sign-in page: Hydra checks them only after the owner consents, and the verifier at `POST /oauth/token`. The app sends PKCE (`code_challenge` S256 to `/oauth/authorize`, `code_verifier` to `/oauth/token`) since 2026-10-26; that day the owner connected with it in development (`OAUTH2`, `OK`, with a refresh token). Whether Nuki refuses a wrong verifier was not tried.
- `GET /oauth/authorize` sends the owner back with `code`, `scope` and the `state` whole; `POST /oauth/token` with the client's id and secret both as HTTP Basic and in the form answers `token_type` `bearer`, `expires_in` 3599, `scope`, `access_token` and, with `offline_access`, `refresh_token`; `grant_type=refresh_token` answers new access and refresh tokens. The refresh token rotates on every refresh; whether the previous one still works was not checked, so the app assumes it does not. Nuki's guide says refresh tokens last 90 days and that, if the access token is not refreshed within them, the owner must authorize again; whether each refresh starts a new 90 days or they count from the authorization, it does not say. The daily check refreshes every owner, so with the first reading no owner ever has to connect again; with the second, every owner would every 90 days (and get the disconnection email). The owner's production connection, made on 2026-10-26, tells on 2027-01-24. The tokens are opaque, not JWTs, so they do not tell either.
- Nuki's rate limits (docs.nuki.io/guide/endpoints/rate-limits): 4 requests per second, 100 per minute, 1000 per hour, then 429 until the window passes; the page does not say whether per token, account or client. One guest's opening (an unlatch and up to about 8 reads of the log) takes more than a day's refreshes; the daily check, 2 requests per owner in a row, would only near 100 per minute at about 50 owners, if the limit is per client.
- Nuki's consent page ("A welcome-home le gustaría:") lists each scope with Nuki Web's labels for API tokens, seen with all four on 2026-10-26: in Spanish, `smartlock.log` "Ver el protocolo de cierre y recibir notificaciones de registro", `smartlock.readOnly` "Ver dispositivos", `offline_access` "Mantener el acceso a los datos hasta su revocación" (its description says the owner can revoke it at any time), and `smartlock.action` "Gestionar dispositivos" ("Se permite operar dispositivos Nuki"). Then "Cancelar" and "Autorizar"; "Cancelar" sends the owner back with `error=access_denied` and the `state`, which the app tells apart (seen 2026-10-26). Its "No me preguntes de nuevo" remembers the consent; asking for more scopes asks again.

**Going through it in development**, which needs the owner (their passkey, their Nuki account): put the client id and secret in `secrets/config/` as above, `docker compose up -d`, `./gradlew bootRun`, sign in, and at `/settings/nuki` press "Conectar con Nuki". The token then carries `smartlock.action`, which opens a real door: create no access link while that connection exists, and disconnect at the end.
