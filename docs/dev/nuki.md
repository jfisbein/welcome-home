# Nuki

Read when: anything that calls Nuki, connects an owner to it or reads what it reports: connections, tokens, OAuth2, the unlatch, Openers.

See also: [what was learned about Nuki](nuki-learned.md) (how Nuki behaves, as found by hand), [guest flow](guest-flow.md) (what asks for the unlatch), [status](status.md) (what only real use will tell).

## LockProvider

**`LockProvider`** (`findConnection`, `listLocks`, `getSnapshot`, `listSnapshots`, `unlatch`, `getRecentLog`, all by owner id) is all the other modules may ask of Nuki, and what it is for is the tokens: they are decrypted inside `nuki` and never leave it. It has one implementation and is not there to have another: a local Nuki Bridge or MQTT in place of the Web API was decided against on 2026-11-05 (review item SIM-11, 2026-11-20, as its javadoc and this page gave that as its reason).

## Decisions

| Decision | Why |
|----------|-----|
| Owners connect Nuki only by authorizing welcome-home's OAuth2 client; without a client id and secret nobody can (taken out on 2026-11-20: review item SIM-02, the owner's choice) | Until 2.18.0 an owner could instead paste an API token made in Nuki Web, which was the only way before Nuki granted the client (2026-10-25) and let an install work without one. It was a second path at every step: its own checks, its steps in five languages quoting Nuki Web's labels, a way to disconnect that could revoke nothing, and a branch wherever a token is refreshed or tried again. With the client granted and nobody using a pasted token, it went, with `nuki_connection.credential` (changeset 039, with which major version 3 began). What it costs: an install from the public repository must ask Nuki for the Advanced API first, and if Nuki ever takes the client away, nobody connects until it is back; those connected go on while their tokens refresh. |
| The OAuth2 client written in `nuki` (`NukiAuthorizationController`, `NukiOAuthClient`), not Spring Security's | Spring's stores tokens in clear, and its token client would need customizing for Nuki anyway; what it would save, the `state`, the PKCE verifier and the redirect, is a few lines, covered by `NukiAuthorizationTests`. |
| OAuth2 tokens in `nuki_connection`, each encrypted for its owner and kind; one refresh at a time per owner, 5 minutes before expiry; a token request never repeated once Nuki may have answered | Nuki rotates the refresh token: two refreshes with one, or a repeated one, would leave a dead token. A refresh failure is never `NO_ANSWER`, which would tell a guest that the door may have opened. |
| 2.0.0 renamed `api_token_encrypted` to `access_token_encrypted` | Nobody but the owner used the app yet; the changeset has a `<rollback>`, checked once both ways, and the dump taken before upgrading restores 1.x. |
| A 401 disconnects only if a read repeats it, and a disconnection is tried again hourly for 7 days | Disconnecting stops every link of the owner, so a passing mistake of Nuki's must not do it, nor last until the owner notices. Credentials stay stored while disconnected, which makes trying them cheap; 7 days bounds the requests for an access truly revoked. The owner is emailed both ways, under the same preference. |
| Disconnecting Nuki or deleting an owner revokes an OAuth2 authorization at Nuki, best effort, and so does an authorization that is not stored: one without every scope or the refresh token, or whose check failed (review item SEC-16, 2026-11-20; with its access token when there is no refresh token) | Deleting the tokens here leaves them valid at Nuki, with encrypted copies in dumps for 30 days. Revoking the refresh token ends its access tokens too (RFC 7009). A failure is logged and changes nothing else, as the owner asked to leave. The endpoint is Nuki's `revocation_endpoint`, at `oauth.nuki.io`; a request there without credentials answers 400, and at `api.nuki.io`, 404. It takes the client's credentials only as HTTP Basic: with them also in the form, as the token endpoint takes them, it answers `invalid_client`, so no revocation worked before 2026-11-04. Connecting again does not revoke the tokens it replaces. |
| The daily sync of an owner's locks is the daily check of their connection; there is no job for it | Both read the owner's locks from Nuki with the stored token, 15 minutes apart, and each refreshed an OAuth2 token about to expire and disconnected one that Nuki rejected twice, as every call does (review item SIM-08, 2026-11-19). Reading the locks notes that Nuki accepted the token (`NukiConnections.accepted`, the page's "last checked"). The hourly retry of disconnected connections stays (`ReconnectionJob`), as nothing else calls Nuki for them. |
| Refreshing and re-encrypting tokens are `TokenRefresher`'s, one at a time per owner; what to do with the outcome is `NukiConnections`'s | `NukiConnections` did both and four things more, and wrote the refresh, encrypt and store sequence twice, as the DAO did its SQL (review item SIM-14). One `saveRefreshed` stores what a refresh returned for a connection in the state it was in, and connects a disconnected one again. |
| Unlatch (action 3), confirmed from the lock's log | Nuki runs actions asynchronously: a 204 only means accepted. |
| One way to unlatch, the plain action, and one way to learn what came of it, the lock's log: no Advanced API, no webhooks (taken out on 2026-11-20, review items SIM-01 and SEC-06, the owner's choice) | From 2.5.0 to 2.18.0, owners connected with OAuth2 unlatched through Nuki's Advanced API, whose webhook told a guest in about 2 seconds that the door had opened, where the log takes 5 to 7. Its price was a public endpoint that took requests from outside without a session, a Cloudflare rule for Nuki's address, a fallback to the plain action, a second trip to Nuki on `invalid_scope`, reports matched in memory, and two scopes: `smartlock.auth`, which lets its holder manage a device's authorizations and so made a leak of the tokens worth more than opening, and `webhook.central`. The door opens as fast; only the page's "Puerta abierta" comes some seconds later. What was learned of the Advanced API stays in [what was learned](nuki-learned.md#by-hand), should it ever come back. |
| A Nuki Opener is a lock of another type in the same `LockProvider`, and a smart lock may name one as its building entrance, whose slide its links' guest page shows first | Nuki's Web API lists Openers among its smartlocks and opens them with the same action, so no adapter of its own; and a guest who must pass a building's entrance and then a door needs both from one link (the user's choice, 2026-10-27, over separate links per device). `access_event.lock_id` stays the link's lock, the Opener going in `entrance_lock_id`, so link histories, emails' history links and the previous release keep reading events as before. Nuki does not document how an Opener logs an opening: it is taken to be a lock's unlatch, and an unconfirmed opening logs what the log showed. |
| A refusal at Nuki's token endpoint disconnects an owner only if it is about their code or tokens | A 401, `invalid_client` or `unauthorized_client` is about welcome-home's client, such as a wrong or rotated secret: disconnecting would hit every OAuth2 owner at the next daily check, and correcting the secret would not bring them back. It logs an error and counts as Nuki failing. A 403 or a 404 from the token or revocation endpoint is a Nuki error too (`NukiOAuthClient.notAboutALock`, review item COR-10, 2026-11-20): `NukiRequests` reads them as a missing permission and a lock that is gone, which there they are not, and an owner told of a missing permission would look for one that is there. |
| A lock that Nuki reports offline (`serverState` other than 0) is told to its owner only as something that may keep links from opening, and not at all once an opening has succeeded since the app first saw the report, until an opening fails or is not confirmed, or Nuki reports the lock online and then offline again (`LockReachability`, `lock.offline_since` and `offline_disproved_at`) | Nuki's Web API has reported a lock offline for hours while Nuki's app showed it online and its actions ran (seen 2026-11-13, [what was learned](nuki-learned.md#by-hand)), so the report alone is not proof, and an opening is (the user's choice, 2026-11-13). Only openings by guests count, as they are the actions whose outcome the app learns; an opening before the app first read the report disproves nothing, as nothing says the report was already being made. Only the daily check of every lock starts and ends a report; pages read Nuki now against the report as that check left it and write nothing, so that when a report began does not depend on who looked at a page (review item COR-06, 2026-11-20). The price is up to a day: a lock that went offline since the check is told as offline whatever it has opened, and one that came back and went offline again keeps what was made of its earlier report. A refusal in night mode changes nothing. The report never stops an opening: the unlatch is always sent. The lock's page says "Nuki indica que no tiene conexión, pero ha abierto la puerta desde entonces". |
| The unlatch is retried only on 429 or when no connection was made | Retrying after Nuki may have run it could open the door twice. |
| Nuki tokens that an earlier AEAD key encrypted are encrypted with the primary one on every start, each owner's in their turn among refreshes | A keyset changes only with a restart, so one pass then leaves every token on the primary key, and the earlier one can leave the keyset without owners connecting again; before, pasted API tokens and disconnected connections kept it for good. In their turn: a refresh that read the tokens before they changed would not store Nuki's new ones, and Nuki rotates the refresh token. The earlier key stays 30 days, as the dumps taken before the rotation need it (runbook). |

## Tests

- **Nuki**: never the real API in tests. `NukiStandInConfiguration` starts WireMock in place of `api.nuki.io`; `NukiWebClientTests` covers status codes, timeouts, retries and backoff; `NukiOAuthClientTests` where an owner authorizes, the token endpoint and revoking; `NukiAuthorizationTests` the way to Nuki and every way back; `ReconnectionJobTests` the daily read of every owner's locks as the check of their connections, and the hourly retry; `LockSyncJobTests` (in `locks`) that the sync does that check; `NukiTokenRefreshTests` refreshing (once for simultaneous calls, disconnecting when refused, not when Nuki refuses the client, never `NO_ANSWER`); `NukiConnectionWithoutAuthorizationTests` the app without an OAuth2 client. `TokenReEncryptionTests`: on start, tokens of the AEAD keyset's earlier key encrypted with the new one, whatever the connection's status; a token whose key is gone left as it is; a refresh under way keeping the tokens Nuki returned. The test contexts' AEAD keysets are rotated once, as production's is after a rotation.
