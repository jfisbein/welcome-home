# Links

Read when: changing `links`, the tables `access_link` and `access_link_schedule`, a link's form, its token, its schedule or its PIN.

See also: [guest flow](guest-flow.md) (where the PIN and the schedule are checked), [privacy](privacy.md) (a link's changes in the owner's activity), [database](database.md).

## Decisions

| Decision | Why |
|----------|-----|
| A link's schedule: per day, one range a day, in `access_link_schedule`, apart from `LinkStatus` | Nuki Web's one range for all the chosen days cannot say "Monday to Friday 9 to 17, Saturday 10 to 14" without two links, and so two URLs for a guest (the user's choice, 2026-11-02, for one range per day; `opens_at` in the key leaves room for more). Local times, so 09:00 stays 09:00 when the clocks change. A closing time not after the opening time is on the next day, and a "Todo el día" tick per row, stored as 00:00 to 00:00, is the whole day: the time 00:00 to 00:00 alone was not evident (the user's remark, 2026-11-02). A link's state still says only its dates, as the schedule closes and opens every day. Nuki knows nothing of it: every opening goes through the app. `resolve_link` does not return it, as changing what a function returns takes a `DROP`; the MAC is verified first, so the owner's context can read it. **A rollback to a release before 2.6.0 ignores schedules**, so such links open at any time within their dates: the user accepted this, with a warning in the runbook, as the alternative is a new major version. |
| A link's PIN: optional, encrypted so that its owner can read it, checked in `OpenDoor` after the dates and schedule and before the lock, counted per link in memory | A URL that leaks or is forwarded opened the door for whoever held it, and the MAC cannot help (the user's choice, 2026-11-07, for an optional PIN the owner can see again, over a hash: they send it to the guest apart from the link, and forget it). It is AEAD like the Nuki tokens, bound to the link too, and re-encrypted on start after a rotation (`LinkPinReEncryption`), so the earlier key can leave the keyset. Four to eight digits can be guessed, so the limit is the protection: 5 wrong PINs per link over 15 minutes, from any address, then the link refuses even the right one (`too-many-attempts`), in memory like the other limits. The check runs before the door and the guest's position, so a wrong PIN learns nothing about them; the page asks only after the slide, and the field is a plain numeric text input with `autocomplete="off"`, as a PIN is not an SMS code (`one-time-code` would offer the last SMS) and `type=password` would offer password managers to save it. The owner's field is a password field with an eye (`reveal.js`), shown on the edit page: an owner reads it on their own page, as they read a link's URL. Changing it is an edit of the link, so it is recorded and emailed as one. **A rollback to a release before 2.16.0 ignores PINs**, so such links open without one, as with schedules: the runbook says so. |
| Links are `{link_id}.{HMAC(link_id, token_version)}` | Nothing to steal from the database; a URL can be shown again; incrementing `token_version` invalidates every earlier URL. |

## Tests

- **Links' PINs**: `LinkPinTests` (set, changed and removed from the forms, stored encrypted and bound to its link, read back by its owner alone, refused when not 4 to 8 digits, encrypted again with the new key), `OpenDoorTests` (a PIN asked for before anything reaches Nuki, a wrong one, the right one, one sent to a link without, a link that spent its wrong PINs), `RateLimiterTests`, `GuestPinTests` in Chromium (the form after the slide, typing again after a wrong PIN, told in red, cancelling, axe on the open form), `OwnerPagesTests` (the eye).
- **Links' schedules**: `LinkScheduleTests` (hours, midnight, the clocks changing, the first opening), `LinkScheduleFormTests` (the form, what is refused, a schedule said in each language).
