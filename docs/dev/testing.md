## How tests run

`./gradlew build` compiles (Error Prone, NullAway), runs every test and checks javadoc. Tests start from rows written by `TestData` (owners, locks, links, schedules, attempts, connections, passkeys), so that a change to a table means a change there; a test writes its own SQL only when the SQL is what it checks, such as Row-Level Security or a constraint; what many tests do to a row is a verb there (`deactivate`, `revoke`, `disconnectNuki`, `makeAdmin`, `verifyEmail`). `aRowInEveryTable` gives an owner a row in every table with an `owner_id`, which `ownerTables` reads from the schema: the tests of what keeps owners apart, and of what deleting one takes away, go by it, so a new table is tried without anyone adding it to a list. Most tests are integration tests (`@IntegrationTest`): a real Postgres in Testcontainers, initialised with the production role script, migrated by Liquibase as `migrator`, used by the app as `app_user`, with freshly generated keysets. One Postgres container serves the whole run, whatever the application contexts: tests take turns, and a context that is not running a test does nothing, as `@IntegrationTest` turns every scheduled job off (tests call the jobs themselves).

- **Time**: the app reads the time from a `Clock` bean (`config.TimeConfiguration`), which in tests is `TestTime`: the real clock until a test stops it (`freeze()`, for a test that reasons about today, so that it and the app cannot read two sides of midnight) or sets it (`setTo`, for the classes that send dates in 2030, so that those stay in the future whenever the tests run). `@IntegrationTest` puts it back after each test. The database's `now()` stays the real time, so a test that sets the clock far from it must not rely on rows dated by the database; and how long something takes (the wait for a lock's confirmation) is measured with the real clock. The rate limits have a clock of their own, `TestClock`, which a test moves forward to see a limit come back, and which moves an hour after every test, so that each starts from full limits without an address of its own.
- **Waiting**: with Awaitility, for what is seen to have happened (a request reached the Nuki stand-in, a thread is waiting), never a sleep that hopes it has.
- **Coverage**: JaCoCo measures it on every run of the tests, prints it by package and writes `build/reports/jacoco/test/html/index.html`. No threshold fails the build: it is to look at where it is lowest.

- **JavaScript**: `src/test/java/welcomehome/browser` runs it in headless Chromium, which Playwright downloads when first used, on a real server with the Nuki stand-in, with pages of a phone's size. `GuestSlideTests` slides `open.js` with real touch events (what keeps a touch by mistake from opening, keys, what follows each outcome); `OwnerPagesTests` registers and signs in through `webauthn.js` with Chromium's virtual authenticator, and tries `confirm.js` and `schedule.js`. CI installs the browser's system packages first (`./gradlew installBrowser`).
- **Commands**: `CommandLineTests` starts the app without the web server.

## Practice

- **Practice**: start with `git fetch`: the development clone has been dozens of commits behind `origin/main`, which is where work from other machines and release merges land. Each change is checked with a mutation test by hand (break the code, see a test fail, restore it), and deployment changes are tried on a local copy of the production stack (`COMPOSE_PROJECT_NAME=...` to stay apart from the development database).
- **By hand in a browser**, for what no test runs: how pages look, in light and dark and at phone width, and the scripts with no test of their own (`copy.js`, `share.js`). Run the dev app (`docker compose up -d`, `./gradlew bootRun`) and use Chrome; owner pages need the owner's passkey, which only the owner can use (sessions live in memory, so a restart signs them out). Sample rows go into the development database as its superuser (`docker compose exec -T db psql -U postgres -d welcome_home`) and are deleted afterwards. For the guest page to offer opening without any risk, add a `nuki_connection` with status `OK` and `access_token_encrypted` set to `'\x00'`: the token does not decrypt, so an opening fails as unavailable before anything reaches Nuki. Never with a real token. Chrome's window does not shrink below about 616 px: for phone widths the owner switches on DevTools' device mode, and sizes are read with JavaScript (`innerWidth`, `scrollWidth`).
