# Owners and signing in

Read when: changing `auth` or `admin`: passkeys, invitations, recovery links, sessions, an owner's email or account, what admins may do.

See also: [privacy](privacy.md) (sign-ins in the owner's activity), [notifications](notifications.md) (emails about the account).

## Decisions

| Decision | Why |
|----------|-----|
| Sessions end when what let them in is gone: deleting a passkey ends the owner's other sessions, deleting an owner all of theirs | A lost phone must not stay signed in, and a deleted admin must not keep their role, until the session expires. `OwnerSessions` keeps them in memory, as Tomcat does, so a restart loses nothing it needs. Spring's `SessionRegistry` was not used: it hears of sessions through a session strategy, which `WebAuthnConfigurer` does not set. Nor does it set the strategy that changes the session id on signing in, so `SecurityConfiguration` does. |
| Signing in renews the session's id and its CSRF token, and the cookie is `__Host-session` | The token used to outlive the sign-in: a page on a sibling subdomain could plant a session whose token it knew and, once the owner signed in on it, forge their forms, which `SameSite=Lax` does not stop between subdomains (review item SEC-05, 2026-11-19). `WebAuthnConfigurer` gives its filter no session strategy, so `SecurityConfiguration.ON_SIGN_IN` does both, for the filter and for `InvitationController`, which signs in by hand. The prefix closes the planting itself; it needs `Secure`, so the dev profile keeps `JSESSIONID`. Renaming the cookie ends the sessions open at the upgrade, as every restart does. |
| A passkey's name is made fit where it is stored (`AnnouncingUserCredentialRepository.storedLabel`): stripped, cut to 60 characters, "Passkey" if blank | Spring Security's own `/webauthn/register` checks nothing of it and stores up to 1000 characters, shown on the passkeys page and in emails; the app's forms checked it, that endpoint did not (review item SEC-17). What the app asks of a passkey is one constant, `SecurityConfiguration.PASSKEYS`, for Spring's registration and the invitation's own; the rest of the invitation's options copy Spring's defaults, which it cannot be asked for without saving a user entity for an email not yet registered. |
| Passkeys only, invitations only, and passkeys must verify their user | No passwords to leak; a private app with few, known users. A passkey is the only factor, so registering and signing in require user verification (a PIN, fingerprint or face): a security key without a PIN, which anyone holding it could touch, is refused. Phones, computers and password managers verify anyway. |
| An admin makes an admin of an owner, through the function `make_admin`, and nothing takes the role away (UX-14 of the 2026-11-19 review) | Only a new invitation gave the role, so the only admin could neither leave nor share the work without inviting someone again. A function rather than `GRANT UPDATE (is_admin)`: `app_user` still cannot update the column (`OwnerLanguageTests`), so a flaw in the app can give the role and never take every admin's away. The role is read at sign-in, so it shows at the owner's next one. Taking it away was left out: deleting the account does it, and it is one more way to end with no admin. |
| Admins see only emails and dates | An admin is still just an owner to RLS. Recovery links are the exception the user chose: whoever holds one signs in as that owner, so the admin who creates one could. The owner is emailed when one is created and when a passkey is added, so its use is not hidden from them. |
| An owner changes their email at once, and the new address is verified like a new owner's; the previous one, if verified, is told, and for 7 days also gets the account's notices; their other sessions end | The email is not a credential, as signing in takes a passkey: it is where notices go and the name passkeys know the owner by, so a typo at registration must be fixable without the old address. Notices stop until the new one is verified, as for a new owner. Telling the previous address keeps a change made from someone else's hands from going unnoticed, and so does sending it for a week the notices of what that someone does next, a passkey added or a link created (review item SEC-04, 2026-11-20): `owner.previous_email` and `previous_email_until`, the verified address kept through a second change made before verifying, forgotten by `InvitationPurgeJob`. The other sessions still know the owner by the previous email, so they end; the one that asked goes on under the new one. Passkeys on the owner's devices keep showing the previous email: nothing tells them, and they still sign in. |
| Changing the email and adding a passkey ask for a sign-in within the last 10 minutes (`RecentSignIn`, a time in the session; `RecentSignInFilter`); an owner past it confirms with a passkey at `/settings/confirm` and makes the change again | A few minutes at an owner's unlocked browser were enough to change the email, add a passkey and from then on get every notice (review item SEC-04, 2026-11-20). A filter, not the controllers, as adding a passkey is Spring Security's own endpoints; before `AuthorizationFilter`, so that CSRF has been checked and a visitor who is not signed in still goes to sign in. The page signs in again with `login.js` and goes back to one of two pages it knows, never a URL from the request. A session that never said when it signed in is refused: every sign-in sets it. Connecting Nuki is not guarded, though the report named it: it gives whoever does it nothing of the owner's, and guarding it would only add a step to a flow that already leaves for Nuki and comes back. Deleting a passkey is not either: it is what an owner who lost a device does first. |
| A passkey recovery link lasts 4 hours, an invitation 72 (`InvitationService.RECOVERY_VALIDITY`), and getting in with either is in the owner's activity, a recovery marked `by_recovery_link` | It is the key to an account that already has locks and links, sent by chat to someone waiting for it (SEC-11); and it was the one way someone else may enter an account, an admin among them, that left no entry (SEC-10). A column, not a new kind, which `owner_activity_kind_check` would refuse and a release rolled back to could not name. |
| An owner closes their own account, unless they are the only admin | The admin panel did it for them before, so a mistyped email meant asking an admin. The only admin cannot, as an admin must always be left, as in the admin panel. |
| A recovery never saves again an owner's entry in the passkey store, and signs them in under their email as it is | The entry read when the recovery began carries the email of then, and the store finds a passkey's owner by that name: saved after the owner changed their email, it detached every passkey of theirs (review item COR-04, 2026-11-19). `OwnerRegistration.finish` saves an entry only for a user the store does not know, named by the owner's current email (`namedBy`), which `InvitationController` signs in with too. |
| Deleting a passkey locks the owner's entry in the passkey store first, and deleting an owner locks the admins' rows; `OwnerAccounts.delete` refuses the only admin (`LastAdminException`, 409) | "Never the last passkey" and "an admin is always left" were each one statement or a check before the deletion: two deletions at once each saw the other's row as still there and removed both (review item COR-07). Under the lock the second one waits and counts again. The refusal is in the service now, so no caller can skip it; in the rare race the admin who stays has had their sessions ended and their Nuki authorization revoked by `OwnerDeleting`, which goes first because the deletion takes the tokens with it. |
| Recovery adds a passkey and keeps the old ones | The user's choice; the owner then deletes the lost device's passkey at `/settings/passkeys`, which never deletes the last one. |
| A form from a page whose session ended goes to `/login?expired`, and "Salir" to `/login?logout`, instead of a 403 | Sessions live in memory, so every update in Dockge ends them, and so do 30 minutes without use; the form's CSRF token went with the session, and the owner got a 403 for pressing "Salir" (the user's report, 2026-11-04). Only for an HTML form from a browser that sent a session the server no longer has: a bad token otherwise may be a forged request, and scripts read the 403 themselves. Spring's `invalidSessionUrl` was not used: it would send any request with an ended session's cookie to sign in, an owner opening one of their own guest links among them. |

## For the next major version

**An owner is known by their email, which can change** (review item ARC-01, looked into on 2026-11-19 and left for v3). The session's principal is the owner's entry in the passkey store, whose name is their email: `CurrentOwnerArgumentResolver` finds the owner by it on every request, `OwnerSessions` keys sessions by it, and a trigger gives `user_entities.owner_id` from it. So a change of email renames the entry, rebuilds the session by hand (`AccountController.signInAs`) and ends the owner's other sessions, which know them by the previous one. It cannot be the owner's id without a release that breaks going back: Spring Security's passkey endpoints find, and create, the entry by the authentication's name (`Webauthn4JRelyingPartyOperations`, `findUserEntityOrCreateAndSave(authentication.getName())`), so the name itself would have to become the id. That is a migration of every `user_entities.name` and of the trigger, after which the release before, which signs in by email, cannot run. For v3: name the entry by the owner's id and keep the email as its display name; send the email as the name in the options an authenticator is given (`setCustomizeCreationOptions`, and `OwnerRegistration`'s own), as that is what a passkey shows; `loadUserByUsername` and `CurrentOwner` then go by id, a change of email touches only the display name, and `signInAs` and the ending of other sessions on a change of email can go. What could be done meanwhile is done: a recovery no longer saves a stale entry (COR-04).

## Tests

- **A recent sign-in**: `AccountTests` (a session that signed in long ago changes no email until its owner confirms with a passkey; the page it is sent to goes back only to the app's own pages; the previous address gets the account's notices for some days and is then forgotten), `PasskeyManagementTests` (nor adds a passkey, through Spring Security's endpoints). Tests that add a passkey with `user()` mark their session with `RecentSignIn.ATTRIBUTE`.
- **Admins**: `AdminPanelTests` (who is an admin shows, an owner is made one, an admin or nobody changes nothing, an owner cannot make themselves one, CSRF; a recovery link asks first), `OwnerLanguageTests` (the app may not update `is_admin`), `MigrationCompatibilityTests` (the function, reviewed).
- **Passkeys**: `PasskeyEmulator` (webauthn4j-test) answers registration and sign-in like a browser with an authenticator, so the real WebAuthn endpoints are exercised end to end.
- **Sessions**: `PasskeyManagementTests` (two passkeys deleted at once leave one, and a deletion waits for the owner's entry; deleting a passkey ends the other sessions, signing in changes the session id and the CSRF token, a name too long cut where it is stored), `InvitationRegistrationTests` (registering changes them too), `SessionCookieTests` (the cookie's name and flags), `AdminPanelTests` (a deleted owner's session ends), `AccountTests` (the only admin never deleted, two admins deleted at once leaving one), `PasskeyRecoveryTests` (an email changed while recovering), `EndedSessionTests` (a form from a page whose session ended goes to sign in, against a running server).
